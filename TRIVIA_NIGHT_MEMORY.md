Single source of truth for the Host workspace and Player redesign work. Read this before touching `HostControlPanelPage.tsx`/`.css`, `PlayerRoomPage.tsx`/`.css`, `styles/hostDashboardShell.css`, `styles/liveGameShell.css`, or `components/GameSummaryCard.tsx`.

## 1. Project State

- Host workspace (Invite Lobby → Game Setup → Live Game (Question/Reveal) → Leaderboard/Ended) has had a full UX redesign pass across several sessions. All five screens share one visual language: full-width/wide layouts, no page-level footer bars, floating primary actions, no scroll on desktop (Live Game/Leaderboard) or a naturally-scrolling settings panel (Invite Lobby/Game Setup).
- **Player Lobby redesigned to match**: the Player's entire `lobby`-phase view (both `lobbyStage` "invite" and "setup", now ONE screen - see §2) now reuses the Host Dashboard's own two-column shell verbatim, via a shared stylesheet (`styles/hostDashboardShell.css`) and a shared `components/GameSummaryCard.tsx` - see §2/§4.
- **Player Question/Reveal redesigned to match too** (latest session): the Player's `question`+`reveal` phases (merged into one `PlayerLiveQuestionPhase` component, same "two states, one component" pattern as the Host's own `LiveGamePhase`) now reuse the Host's Live Game header and Question Card verbatim, via a second shared stylesheet (`styles/liveGameShell.css`) - see §2/§3. Every distraction not needed to answer the current Question was removed: no Room Code, no "You're in!", no lobby-era paragraphs, no host-setup info. Player Leaderboard/Ended, the Stage (big-screen) view, Deck Library/Editor, and Quick Play content are untouched.
- **"Estimated Time"** added to Game Summary (`components/GameSummaryCard.tsx`), shown on both the Host Dashboard and the Player Lobby - computed by `estimateGameDurationMinutes` (`config/timingEstimates.ts`) from Question count + Question Timer (or a blended MC/Typed-Answer average when there's no timer) + fixed Reveal/transition/Leaderboard overhead constants. Approximate by design, never a scheduling input - same spirit as the pre-existing per-Deck browsing estimate it sits beside in that file.
- Known issue (not fixed): `teamReadinessProblem` (unassigned players in Team mode) has no visible surface now that Start Game's footer is button-only; only shown via the button's own disabled state.
- Deferred, not implemented: a real per-Deck "Current Standings" checkpoint mid-game with rank-movement indicators (▲▼—) was requested but **descoped** — the app's phase-transition table only ever reaches `leaderboard` once, after the last Question of the last Deck (`reveal: ["leaderboard","question"]`, `leaderboard: ["ended"]` only, no `leaderboard → question` path back in). Building real per-Deck checkpoints needs a new allowed phase transition, deck-boundary-triggered routing, and a rank-history snapshot to diff against — genuine game-logic work, not a layout change. What shipped instead: the single real end-of-game standings moment (`leaderboard`/`ended`) fully redesigned (wide, modern, one continuous screen), no movement arrows (nothing to compare against), no per-Deck preview.

## 2. Architecture

- Single page component `HostControlPanelPage.tsx` renders every Host-side room phase (`lobby/invite`, `lobby/setup`, `question`, `reveal`, `leaderboard`, `ended`) via conditionals keyed on `room.phase`/`lobbyStage`.
- Realtime split: `useRoomChannel` (Presence, ephemeral "who's online") vs `useGameRoom` (Postgres-backed authoritative state: room, players, teams, answers).
- **"Two states, one component" is the core pattern of this redesign**, used twice:
  - `LiveGamePhase` renders both `question` and `reveal` phases, switched only by a `revealed: boolean` prop.
  - `HostLeaderboardPhase` renders both `leaderboard` and `ended` phases, switched only by an `ended: boolean` prop.
  - In both cases every wrapping element renders unconditionally at the same DOM position in both states — only inner content/the action button swaps. Verified live: identical `getBoundingClientRect()` before/after the transition, and the primary action `<button>` is the same DOM node (not remounted) across it. This is what makes Reveal Answer / Show Winner feel like the screen continuing, not navigating. **Never split either pair back into two separate components/screens.**
- Shared Host workspace shell (CSS): `.host-dashboard` (grid: fixed sidebar + main), `.host-dashboard-sidebar` (fixed left room panel, `position:fixed` ≥860px / `position:static` <860px), `.host-dashboard-panel`/`.host-dashboard-content` (right panel shape owner + padded body).
- **This shell now lives in `src/styles/hostDashboardShell.css`, not `HostControlPanelPage.css`** (extracted this session so the Player Lobby can import the exact same rules - see §9). Contains: `.host-dashboard`/`-main`/`-sidebar`(+`-identity`, `.host-sidebar-live`/`-dot`)/`-panel`/`-content`, `.host-floating-action`, `.host-dashboard-header`/`-eyebrow`, `.host-dashboard-section`/`-helper`, `.host-room-status-count`/`-group`/`-group-name`/`-roster`, `.host-dashboard-summary-list`/`-row`, `.host-roster-more`, `.host-lobby-code`, `.host-style-note`. Both `HostControlPanelPage.tsx` and `PlayerRoomPage.tsx` import it before their own page CSS. Host-only pieces (`.host-dashboard-select`, `.host-style-picker`, `.host-dashboard-back`-adjacent styling, `.invite-qr`'s own base rule) stay in `HostControlPanelPage.css` - the Player page never renders them.
- `.live-game` (Question/Reveal) and `.host-leaderboard` (Leaderboard/Ended) are both wide, sidebar-free, full-viewport screens (`max-width: var(--max-content-width)`, no scroll ≥860px) — distinct from the two-column Dashboard shell.
- **The Live Game header + Question Card shape now lives in `src/styles/liveGameShell.css`** (extracted this session, same reasoning as hostDashboardShell.css), shared by the Host's `LiveGamePhase` and the Player's `PlayerLiveQuestionPhase`. Contains: `.live-game-header`/`-eyebrow`/`-category`, `.live-game-timer`(+`-urgent`), `.live-game-question`(shape - `grid-area: question` included but harmless outside a grid ancestor)/`-prompt`/`-answers`(wrapper), `.live-game-answers`(grid)/`-answer-card`(+`-correct`)/`-answer-letter`/`-answer-text`/`-answer-correct-tag`, `.host-typed-answer-key`. Both pages import it before their own page CSS. **Layout containers stay page-specific** (genuinely different): Host's `.live-game` is a two-column grid (Player Monitor + Question Card, `.live-game-question`'s height driven by a grid row's `1fr`) with a bottom-padding reservation for `.host-floating-action` layered on top of the shared shape in `HostControlPanelPage.css`; the Player's `.player-live-game` (`PlayerRoomPage.css`) is a simpler single-column flex wrapper (no monitor column, no floating action - a Player has nothing to moderate), `.live-game-question`'s height driven by `flex: 1`, fixed-height at *every* width including mobile (stricter than the Host's own ≥860px-only no-scroll guarantee - see §3).
- `.live-game-answer-card` is a read-only `<div>` on the Host page (always shows `.is-correct` - Host-only foreknowledge) but a real `<button>` on the Player page (`.is-correct` only once `revealed`); `.player-answer-button` (`PlayerRoomPage.css`) is the interactive-element reset layered on top of the same shared shape, never touching padding/radius/min-height/gap.
- `--app-header-height` (68px, `variables.css`) is what every sticky/fixed Host element offsets from. `scrollbar-gutter: stable` on `html` prevents the fixed sidebar shifting between short/tall pages.
- **Floating primary action pattern** (`.host-floating-action`, global class): no footer surface at all — `position: fixed` ≥860px, aligned to the right edge of the current screen's own content grid (via a per-screen `--host-panel-right-inset` custom property, redeclared with the same formula on each wide screen's own wrapper, mirroring the viewport-centering math `.host-dashboard-sidebar` uses for its own `left`), `bottom: var(--space-lg)`, `z-index: 10`. Below 860px it's a plain static full-width button at the end of the content flow (no fixed positioning — sidesteps mobile safe-area/keyboard/address-bar issues entirely). Used by: Invite Lobby's Continue, Dashboard's Start Game, Live Game's Reveal Answer/Continue Anyway/Next Question/Finish Deck/Finish Game (a sibling of `.live-game-question`, not embedded in the Question Card — see below), and the Leaderboard's Show Winner/Play Again. On `.live-game` (the only floating-action host of these that's `display:grid` rather than flex/block), the button is an unassigned grid child with `grid-column: 1 / -1` so it auto-places into its own row below 860px; from 860px on it's `position: fixed` and out of grid flow entirely, same as everywhere else.
- Breakpoint convention: **860px is the ONE Host-workspace breakpoint** (sidebar fixed↔static, all two-column↔stacked layouts). Never introduce a competing one. The Player Lobby reuses this exact breakpoint too (it's baked into the shared shell CSS, not redeclared) - do not give Player its own tablet/mobile breakpoint.

## 3. UI / UX Decisions (approved, final)

- **No footer bars anywhere in the Host workspace.** The old sticky translucent action-footer (Dashboard/Lobby) and the old page-level Reveal-Answer footer (Live Game) are both gone, replaced by `.host-floating-action` (see §2). Only the primary button is visible — no background plate, no border, no summary/readiness text beside it.
- Host Dashboard/Invite Lobby: fixed left room panel (QR, Room Code, Live status, Open Stage, optional Back to Invite) never moves/resizes; right panel content ends naturally with its own rounded corners (no footer child forcing square-then-rounded corner logic anymore).
- Sidebar vertical rhythm: 3 regions (Back-to-Invite / QR+Code+Live cluster / Open Stage), `gap: var(--space-lg)` minimum, `margin-block:auto` on the middle cluster.
- Genuine action-failure messages (`startError`/`continueError`) render as a conditional alert inside the panel's own content, above the floating button — never fabricated copy, never inside/beside the button itself.
- Dashboard content reserves bottom clearance (`padding-bottom: calc(space-lg*2 + space-md)` ≥860px) so the last row (Game Summary) can always be scrolled fully above the fixed button.
- Deck cards: portrait `aspect-ratio: 3/4`, identical filled/empty dimensions.
- **Live Game Control Center** (`question`+`reveal`, one screen): header (question X of Y, category, large timer — never moves between the two states) + two-column body, 30%/70% (Player Monitor / Question Card). The Question Card is now a pure content container - prompt then answer area (`.live-game-question-answers`, `flex:1`) only, no footer, no divider, no internal scroll container. The primary action is a `.host-floating-action` sibling of the card (see §2/§6), the same fixed bottom-right pattern as every other Host screen. Both columns are grid-stretched to equal height, and the card reserves `calc(space-lg*2 + space-md)` of bottom padding (≥860px, identical formula to Dashboard/Leaderboard) so the floating button never sits on top of the last answer row.
  - **No internal scrollbar, ever** (redesigned this session - see §9): the old `.live-game-question-body { flex:1; overflow-y:auto }` desktop rule, combined with the in-card footer + oversized padding, is what produced an always-present scrollbar; removed entirely. The prompt uses `clamp()` typography; the answer grid is a *fixed* `repeat(2, 1fr)` at ≥860px (not `auto-fit`, which drifted to 3 columns on this card's real ~700px content width) with rows sized to content (not stretched to fill the card) and `align-content: center` to distribute leftover height as breathing room instead of oversized cards. Answer cards use `min-height: 4.25rem` (not a forced stretch) so all four read as equal height for realistic (<=2-line) content without ballooning on large screens. Verified with zero scrollbar/overflow at 1920x1080 down to 1024x768, tablet (768px, auto-fit still yields 2 columns pre-860px breakpoint), and mobile (390px, single column, static full-width button) - and confirmed graceful (still no scroll/clip, just an uneven row) even with a synthetic 3-line question + 3-line answer, beyond the recommended limit below.
  - **Deck Bible content limits** (recommended, not enforced): Question <=2-3 lines; Answer options prefer 1 line, max 2; no `explanation` field exists (unchanged, see below) so no limit needed there.
  - Pre-Reveal left panel: Answered/Waiting rosters (✓/⏳ icon + text per row), Pause/Resume Timer control underneath.
  - Post-Reveal left panel: heading becomes "Player/Team Results"; rosters become four outcome groups — Correct/Incorrect/No Answer/Pending Review (icon+text on the **group label**, not per row; only non-empty groups render) — plus an always-true summary line ("5 Correct · 2 Incorrect · 1 No Answer"). Pause/Resume Timer is removed entirely (answers are locked). Grouping is a pure client-side derivation of `gradingStatus` on the same already-fetched `AnswerRecord`/`TeamAnswerRecord` rows (`revealAndScore` grades+scores atomically before flipping `phase`, so it's already authoritative by the time any client sees `reveal`) — no new grading logic, no new reads.
  - Action button (now a `.host-floating-action`, not inside the card): `Reveal Answer` → `Continue Anyway — Scores May Still Change` (ghost, pending Typed-Answer review outstanding) → `Next Question`/`Finish Game` (nothing pending). `TypedAnswerReviewQueue` renders inside the Question Card, below the answer area, when applicable - it and the pre-Reveal error message are the one known edge case not covered by the "always fits" guarantee above (see §9).
  - No `explanation` field exists in the `Question` data model (by design, see `data/questions.ts`) — no explanation UI, not even an empty section. (The redesign brief that removed the scrollbar also asked for an optional compact explanation slot; skipped for this same reason, consistent with the standing rule.)
  - Standalone QR/Room Code/Open Stage fallback card is suppressed on `question`, `reveal`, `leaderboard`, and `ended` (no reason to invite mid-game or post-game).
- **Host Leaderboard/Ended** (`leaderboard`+`ended`, one screen, `HostLeaderboardPhase`): wide (`--max-content-width`, no sidebar), header ("Final Results" eyebrow / "Current Standings" → "Trivia Complete" h2 / "{N} Questions Complete" progress), ranked list (medal for top 3, rank/name/score, generous padding, `justify-content: space-evenly` so few rows still fill the screen instead of sticking to the top), floating Show Winner → Play Again action. `ended` adds a winner-celebration banner (🏆, name(s), points) above the same list using existing gradient/glow tokens — no separate winner page. Renders its own rows (reusing `sortLeaderboard`) rather than the shared `CompetitorLeaderboard` component, which Player/Stage still use unchanged.
- Mobile-first throughout: every floating action becomes a plain full-width in-flow button <860px; Live Game and Leaderboard both stack to single column, auto height.
- Accessibility baseline across all of the above: never rely on colour alone (icon+text pairing everywhere); `role="status"` for one-time polite announcements, never per-row; DOM/tab order matches visual order except Live Game's deliberate footer-before-monitor desktop tab order.

## 5. Data Model (fields future work depends on)

- `RoomRecord.phase`: `lobby|question|reveal|leaderboard|ended`. Allowed transitions (`types/game.ts`): `question→reveal`, `reveal→{leaderboard,question}`, `leaderboard→ended`, `ended→lobby`. **No `leaderboard→question` path** — this is why there is only one standings moment per game (see §1).
- `GamePlanSection`/`findSectionForQuestion` (`utils/gamePlan.ts`) already track which Deck each Question belongs to — deck-boundary detection is cheap if per-Deck checkpoints are ever built, but routing through one requires the phase-transition change noted in §1.
- `AnswerRecord`/`TeamAnswerRecord.gradingStatus`: `ungraded|correct|incorrect|pending_review`. Authoritative the instant `phase==="reveal"` (graded+scored atomically in `revealAndScore`).
- `Competitor` (shared Player/Team shape): `{ id, displayName, score, tiebreakAt }`. `score` is a live cumulative total, not a history — no per-checkpoint snapshots exist anywhere.
- `RoomPlayer` (Presence-only) has no team field — team assignment only exists via `PlayerRecord.teamId` from Game Setup onward. The Host itself is never a `Competitor` (filtered out of `scorablePlayers`) regardless of `hostParticipation` — that field's scoring behavior is explicitly unimplemented (see its own doc comment).
- `PlannedGame.planSummary` (`PlannedGamePlanSummary`) is deliberately Question-content-free (Deck titles/counts only, no `questionIds`/answers) - see its own doc comment in `utils/gamePlan.ts`. This is what makes it safe to broadcast to every Player/Stage over the same realtime `rooms` row they already subscribe to, and is why the Player Lobby's Game Summary (§3) needs no extra fetch/RPC of its own to show Decks/Questions/timer/flow before Start Game.

## 6. Important Rules

- Reuse shared classes/components instead of duplicating markup (`HostRoomPanel`, `.host-dashboard-*`, `.live-game-*`, `.host-floating-action`, `GameSummaryCard`).
- The Host Dashboard shell (`styles/hostDashboardShell.css`), the Live Game shell (`styles/liveGameShell.css`), and `GameSummaryCard` are all shared between `HostControlPanelPage.tsx` and `PlayerRoomPage.tsx` - a visual/behavioral change to any one of them affects **both** pages. Before editing any `.host-dashboard-*`/`.host-room-status-*`/`.host-floating-action`/`.host-sidebar-live*`/`.live-game-header`/`.live-game-question*`/`.live-game-answer*`/`.host-typed-answer-key` rule or `GameSummaryCard` itself, check both pages' current appearance, not just the one you're working on.
- 860px is the one breakpoint — never a competing one. The Player's Question/Reveal screen is the one exception to "no-scroll only matters ≥860px": it guarantees no-scroll at *every* width, including mobile (see §3) - a stricter, later requirement than the Host's own Live Game.
- Never fabricate a feature not backed by real state/handlers (no explanation UI, no movement arrows, no Deck-checkpoint routing — all explicitly out because the data/transitions don't exist).
- Result/outcome colour lives on group labels (icon+text), never colour-alone on individual rows. No red/error token exists in the palette — reuse `--color-orange` for "needs attention" (Incorrect, alerts), `--color-teal` for "positive" (Correct, Answered, podium).
- `LiveGamePhase` and `HostLeaderboardPhase` must each stay ONE component — do not reintroduce separate Reveal or Ended screens.
- Prefer IntersectionObserver over scroll polling when position-based logic is genuinely needed; verify empirically.
- This Browser pane never composites frames — screenshots fail, CSS transitions/animations never tick, IntersectionObserver callbacks never fire here. Verify layout via `getBoundingClientRect`/`getComputedStyle`, not screenshots/timing.

## 9. Things Future Claude Must Never Forget

- Question/Reveal and Leaderboard/Ended are each ONE component apiece — the single most load-bearing architectural fact of this redesign. Never split either pair back into two screens; never make their transition buttons navigate or remount the tree.
- There is only one real leaderboard moment in this app's current architecture (see §1/§5) — do not build or describe a per-Deck standings feature as if it already exists.
- No footer surfaces anywhere in the Host workspace anymore — only `.host-floating-action`, which is fixed+right-aligned-to-content ≥860px and a plain static full-width button below it. Don't reintroduce a background plate/bar. This now includes Live Game's Reveal/Continue/Next Question/Finish Game button, which used to live inside the Question Card (`.live-game-question-actions`, deleted) — don't put it back inside the card. The Player's own Question/Reveal screen never had a primary action of its own to begin with - a Player has nothing to moderate, so don't add one.
- **The Question Card must never scroll internally, at any breakpoint.** The old `.live-game-question-body { flex:1; overflow-y:auto }` (desktop-only) was the scrollbar's actual cause, produced by that rule combined with the old in-card footer and oversized (`--space-lg`, 40px) padding eating into the fixed-height card's budget - fixed by removing the card-level footer entirely (see above), shrinking padding, using `clamp()` typography, and forcing a real 2-column answer grid (`repeat(2,1fr)`, not `auto-fit`) sized to content rather than stretched. If a future change reintroduces a fixed/bounded height on this card (or on `.live-game` itself, `calc(100vh...)` at ≥860px), re-verify with real `getBoundingClientRect`/`scrollHeight` vs `clientHeight` checks (see below) before shipping - don't assume it still fits.
- `scrollbar-gutter: stable` on `html` is load-bearing for the fixed sidebar's pixel-stable position — do not remove.
- `RoomPlayer` (Presence) has no team field; the Host is never a `Competitor`.
- Do not add new validation/game-state logic while doing layout work — every grouping/derivation introduced this session (Answered/Waiting, Correct/Incorrect/No Answer/Pending Review, ranked list) is a pure client-side read of already-fetched data.
- This dev environment's Vite server can throw a transient `ReferenceError`/`SyntaxError: <X> has already been declared` right after a large same-file edit or a file deletion (stale Fast Refresh/HMR module-graph state in that specific browser tab) — a same-tab reload is **not always enough** to clear it (seen directly this session, right after deleting `PlayerList.tsx`/`.css`); opening a genuinely fresh tab and navigating there did. Never reproduced in `tsc --noEmit`/`vite build` - always check the production build first, and if the dev preview still errors after that, try a fresh tab before concluding the code is broken.
- This Browser pane never composites frames - screenshots fail, CSS transitions never tick. Layout/scrollbar verification must use `el.scrollHeight > el.clientHeight` + `getBoundingClientRect()` via `javascript_tool`, not screenshots. The `javascript_tool` execution context persists across calls in the same tab (top-level `const`/`let` redeclare errors on a second call with the same variable name) - wrap each snippet in an IIFE.
- The Host's `handleChangeStyle` (Solo↔Team) calls native `window.confirm()` whenever switching away would disband existing competitors (`teams.length > 0` in Team mode, any non-host `players` row in Solo mode) - this blocks/cancels silently under this Browser pane's automation (no dialog-handling API seen). To test a style switch live, use a **fresh room with no competitors yet** (or the picker while still on the default style) rather than fighting the dialog on an already-populated room.
- **`GameSummaryCard`, `styles/hostDashboardShell.css`, and `styles/liveGameShell.css` are all shared between Host and Player** (see §6) - verified live twice now: switching Solo↔Team/creating a Team/changing any Game Setup control (Lobby session) and picking a Multiple Choice answer/submitting a Typed Answer/pressing Reveal Answer (Question/Reveal session) all reflected on the Player tab within one realtime round-trip, using the exact same shared rendering path. Any future edit to any of the three shared files must be checked on both pages, not just the one being worked on.
- **A Player must never see which Multiple Choice option is correct, or a Typed Answer's correct text, before the Host actually reveals it** - unlike the Host's own Live Game page, where `.is-correct`/`.host-typed-answer-key` are Host-only foreknowledge shown from the moment the Question starts. On the Player page, both are strictly gated on `revealed` (`PlayerAnswerGrid`/`PlayerTypedAnswer` in `PlayerRoomPage.tsx`) even though they reuse the identical shared classes/markup shape. Don't "simplify" by removing that gate just because the Host's version doesn't have one.
- An answer stays changeable up until Reveal on the Player page (existing `submitAnswer`/`submitTeamAnswer` behavior, deliberately preserved - see §3's own "judgment call" note). If a future brief explicitly wants submissions locked after the first tap, that's a real game-logic change, not a pure restyle - confirm before implementing.
- Room Code / "You're in!" / any lobby-era text must never reappear on the Player's Question/Reveal screen (see §3) - if a future change needs to show connection status there again, it belongs in a small, calm element consistent with the rest of that screen's minimalism, not a reintroduced banner.
- The Player's Question/Reveal screen must never scroll internally **at any width, including mobile** - a stricter guarantee than the Host's own Live Game (≥860px only). Achieved via a fixed-height flex wrapper (`.player-live-game`) applied unconditionally, not gated behind a media query the way the Host's `.live-game` is.
- **In this Browser pane, the `computer` tool's synthetic click on a `.player-answer-button` (and possibly other React-controlled buttons) did not reliably trigger React's `onClick` handler** during this session, even though `read_page` showed the element as interactive and un-disabled - `element.click()` via `javascript_tool` worked every time. If a click via `computer` appears to do nothing (no state change, no console error), retry with a direct DOM `.click()` before assuming the code is broken.
